# PrefxPy 保守ガイド

このドキュメントは **機能を増やさない前提** で、PrefxPy を長く小さく保つための考え方・計画・チェックリストです。  
公開手順は [`PYPI.md`](PYPI.md)、設計方針は [`設計.md`](設計.md) を参照。

ロードマップや Issue / Milestone への作業分解はしない。  
定期作業の正本はこのファイルとする（外からのバグ報告・質問用の Issue を汚さないため）。

---

## 1. 基本的な保守運用の考え方

個人 OSS でも、保守は「新機能を足す」より **決まった確認を繰り返す運用** に近い。  
方針をリポジトリに書いておくのは OSS では普通のことです。

- 数ヶ月空いても、何を見るかが迷わない
- 「何をやらないか」を明文化して、機能肥大を防ぐ
- Python / 依存の追従を、その場の気分に任せない

| やる | やらない |
|------|----------|
| 動くこと・分かりやすさ・依存の健全さ | 本番プロキシ化、WebSocket、HTML rewrite など |
| サポート中の Python を CI で守る | かなり古い版まで無理に広げる |
| 小さな修正・ドキュメント整備 | 機能追加のための大きな設計変更 |

迷ったら **「この変更はローカルで prefix / X-Forwarded-* を再現する役に立つか？」** で判断する。立たないなら入れない。

設計メモの「将来の拡張」はアイデア置き場であり、実装予定表ではない。

## 2. バージョン番号

SemVer の **一番右（patch）** を、メンテ公開のたびに上げる。

例: `0.1.3` → `0.1.4` → `0.1.5`

| 変更の種類 | バージョン |
|------------|------------|
| 依存更新・バグ修正・文言改善など、PyPI に出すメンテ | **patch**（`0.1.x`）を上げてタグ公開 |
| docs だけの整理で PyPI に出さない | 番号はそのまま。Git に commit するだけ |
| 使い方や設定の意味が変わる破壊的変更 | 0.x でも CHANGELOG に理由を書く。必要なら minor（`0.2.0`）を検討 |
| 機能追加 | 原則しない。やるなら scope を狭くし minor を検討 |

上げるときは次を揃える。

- `pyproject.toml` の `version`
- `prefxpy/__init__.py` の `__version__`
- `CHANGELOG.md`
- （PyPI に出すなら）`vX.Y.Z` タグ → [`PYPI.md`](PYPI.md)

## 3. サポート方針

### Python

- 下限: `requires-python`（現状 `>=3.10`）
- 上限: 最新安定版まで、余裕があれば CI に足す
- EOL になった版は CI から外す。必要なら下限を上げて patch / minor で出す
- かなり古い版への対応はしない

### 依存パッケージ

対象: `aiohttp`, `httpx`, （3.10 のみ）`tomli`、および `dev` の pytest / ruff。

- 逐次チェック（月次〜四半期で十分）
- セキュリティ／重大バグは優先して上げる
- 上げたら `pytest` を通し、ランタイム依存を変えたら [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) を更新

```bash
pip index versions aiohttp
pip index versions httpx
pip install -U -e ".[dev]"
pytest
```

- [ ] 依存の更新チェックと `pytest`

- [ ] 公開フロー（Trusted Publishing）が生きているか（必要なら TestPyPI）
- [ ] README・仕様・この保守ガイドの軽い見直し

### 機会があれば

- [ ] CI に新しい安定 Python を追加
- [ ] FastAPI / Flask / Django の最小疎通メモ
- [ ] Dependabot 等（任意）
- [ ] バナー・404・設定エラーの分かりやすさだけ直す（機能追加ではない）

### やらないリスト

- HTML/JS の自動 rewrite
- WebSocket 中継
- 本番向け性能・クラスタ・TLS 終端
- 複雑なルーティング DSL
- UI 付きダッシュボード

## 5. 定期ルーチン

### 四半期（15〜40分）

1. GitHub Actions の直近失敗がないか
2. `aiohttp` / `httpx` のリリースノートをざっと見る
3. `pip install -U -e ".[dev]" && pytest`
4. Python のサポート状況を確認
5. 直すものがあれば小さな変更 → CHANGELOG →（出すなら）patch + タグ

### 年次（30〜60分）

1. `requires-python` と CI matrix が現実と合っているか
2. README / 仕様の「非目標」がまだ正しいか
3. この `docs/保守.md` が古くなっていないか
4. Trusted Publishing がまだ有効か

---

## 6. 触るときの最小フロー

```text
変更
  → pytest
  → CHANGELOG（必要なら）
  → push（CI）
  → PyPI に届けるなら patch を上げて tag（PYPI.md）
```

---

## 7. 「うまく保守できている」状態

- サポート対象 Python で CI が通る
- 依存が極端に古くない／深刻な脆弱性を放置していない
- README と実装の約束が一致している
- 公開手順に従えばまた出せる

機能が増えていなくても問題ない。細かい公開手順は [`PYPI.md`](PYPI.md) へ。
